# Audio Forge 项目经理交接说明

本文面向项目经理和后续交付团队，用于快速了解当前 Python 桌面应用的业务定位、技术架构、打包现状、性能风险和后续商业化交付重点。

## 1. 项目基础与架构树

### 应用简介

Audio Forge 是一款 Windows 桌面端 AI 音频工作台，面向“导入歌曲、分离人声/伴奏、滚动歌词、跑调处理、改词唱预研、混音导出”的本地化处理场景。

### 当前业务能力概览

- 歌曲导入：支持将 MP3/WAV/FLAC/M4A 等常见音频导入到本地 `save/` 工程目录。
- 人声/伴奏分离：当前以 Demucs sidecar/外部 Python 环境为主，分离结果存入每首歌工程目录。
- 双轨播放：支持人声音轨、伴奏音轨独立音量控制和列表播放。
- 歌词识别与滚动：支持 faster-whisper 识别，中文结果会尽量规范为简体中文；无歌词时可提示生成。
- 跑调处理：当前为“跑调程度”版本，尽量保持原音色，并通过 rubberband/内部 DSP 路径生成预览。
- 改词唱：当前已改为 ACE-Step 模型服务路径，不再走本机轻量兜底；此功能仍属于重点预研和交付风险项。
- 导出：支持离线混音导出，保留后续 VST/效果链扩展边界。

### 目录结构

为避免把本地打包产物、模型和用户歌曲工程展开成超大树，下面是人工整理后的核心结构：

```text
audio_forge/
├─ core_engine/              # 核心业务引擎，尽量不依赖 UI
│  ├─ ai_singer/             # 改词唱/外部 AI 后端配置边界
│  ├─ dsp/                   # 跑调、F0、人声残留抑制等 DSP
│  ├─ exporter/              # 混音导出
│  ├─ external_tools/        # ffmpeg、rubberband 等外部工具调用
│  ├─ importer/              # 歌曲导入、标准化、工程 manifest 写入
│  ├─ library/               # 歌曲库扫描和会话加载
│  ├─ lyrics/                # LRC/SRT 解析、歌词同步
│  ├─ player/                # 双轨播放、人声分离、sounddevice 输出
│  └─ transcription/         # faster-whisper 歌词识别适配器
├─ ui/
│  ├─ main_window.py         # PyQt6 桥接层、状态管理、后台任务、入口
│  └─ qml/
│     └─ SingleScreenUI.qml  # 单屏 QML 主界面
├─ harness/
│  ├─ cli_harness/           # 无 UI 命令行验证入口
│  └─ eval_harness/          # 音高、延迟等评估脚手架
├─ scripts/
│  └─ packaging/             # PyInstaller spec 和 Windows 打包脚本
├─ docs/
│  ├─ runbooks/              # 打包、运行等操作说明
│  └─ 开发记录/              # 阶段开发记录
├─ plugins/
│  ├─ models/                # 本地模型/ffmpeg/rubberband，不提交
│  ├─ runtime/               # ACE-Step、Demucs 等外部运行时，不提交
│  └─ vst3/                  # VST 插件落点
├─ save/                     # 用户歌曲工程、分离结果、歌词，不提交
├─ user_data/                # 配置、最近状态、日志、缓存，不提交
├─ tests/                    # 自动化测试
├─ pyproject.toml
└─ README.md
```

### 架构设计

当前不是 Web 前后端架构，而是“桌面 UI + 本地核心引擎 + 外部模型/工具进程”的桌面应用架构。

- UI 层：`ui/qml/SingleScreenUI.qml` 负责界面渲染、交互、布局和视觉状态。
- 桥接层：`ui/main_window.py` 中的 `WorkbenchBridge` 通过 PyQt 的属性、槽函数和信号把 QML 与核心业务连接起来。
- 核心引擎：`core_engine/` 承担导入、播放、分离、歌词、跑调、导出等实际业务逻辑。
- 外部能力：Demucs、ACE-Step、ffmpeg、rubberband、faster-whisper 等以本地模型、外部工具或 sidecar 运行时方式接入。

整体上，界面渲染与重计算已经有初步分离：导入、歌词生成、跑调渲染、导出、改词唱等耗时任务使用 `QThread` 或外部进程执行，避免直接堵塞 GUI 主线程。不过 `ui/main_window.py` 仍承担较多职责，后续需要拆分以降低维护成本。

## 2. 技术栈与环境依赖

### 核心环境

- Python：项目声明 `>=3.11`，当前开发环境为 Python 3.11.14。
- 目标操作系统：当前主要面向 Windows 桌面端交付。
- 当前运行方式：开发期依赖本机虚拟环境；交付期目标是便携版或安装包，用户不需要手动安装 Python 环境。

### GUI 框架

- 框架：PyQt6 + QML。
- 入口文件：`ui/main_window.py`。
- 主界面：`ui/qml/SingleScreenUI.qml`。
- 设计目标：单屏工作台、深色/亮色主题、左侧歌曲列表、中间歌词舞台、右侧 DSP/AI 工作舱、底部播放和参数控制。

选择 PyQt6/QML 的原因是它比 Tkinter 更适合现代桌面 UI，也比 Electron/Tauri 更适合本项目的本地音频计算和 Python AI 生态接入。

## 3. 打包与安装部署目标

### 当前打包方案

当前使用 PyInstaller 打包 UI 版本：

- Spec：`scripts/packaging/audio_forge_ui.spec`
- 构建脚本：`scripts/packaging/build_windows_ui.ps1`
- PyInstaller 输出：`dist/audio-forge-ui/audio-forge-ui.exe`
- 便携版输出：`release/AudioForgePortable_next/`

UI spec 目前会收集：

- QML 资源：`ui/qml`
- README 和打包 runbook
- Demucs runner
- 可选 ASR 依赖：`faster_whisper`、`ctranslate2`、`av`、`tokenizers`、`onnxruntime`、`huggingface_hub`、`tqdm`
- 本地模型：如果 `plugins/models/faster-whisper/small|base/model.bin` 存在，会被纳入
- rubberband：如果 `plugins/models/rubberband/rubberband.exe` 存在，会被纳入

同时显式排除部分重依赖：

```python
excludes=[
    "librosa",
    "pyworld",
    "torch",
    "torchaudio",
    "torchvision",
    "scipy",
    "numba",
    "llvmlite",
    "pytest",
]
```

### 安装包期望

当前是便携版交付形态，用户可以进入 `release/AudioForgePortable_next/` 双击启动程序或启动脚本。后续商业交付建议增加安装向导：

- Windows 优先考虑 Inno Setup 或 NSIS。
- 如果需要企业内分发，也可评估 MSIX。
- 安装器需要处理桌面快捷方式、开始菜单、卸载、模型包/运行时目录、日志目录和用户数据保留策略。

### 资源处理方式

运行时目录建议保持如下约定：

- `save/`：用户歌曲工程、原始音频副本、标准化音频、分离 stems、歌词、改词版本。
- `user_data/`：用户配置、最近状态、日志、缓存。
- `plugins/models/`：离线模型、ffmpeg、rubberband 等可替换资源。
- `plugins/runtime/`：ACE-Step、Demucs sidecar 等大体积运行时。
- `_internal/`：PyInstaller 内部依赖目录。

这些目录中，`save/`、`user_data/`、`plugins/models/`、`plugins/runtime/` 都不应提交到远程仓库。

### 当前已知打包风险

- 正式交付不能依赖开发机的 `D:\uv\venvs\audio_forge`。
- Demucs、ACE-Step、torch、模型权重体积大，不适合全部无脑塞进主程序。
- ACE-Step 在无 NVIDIA 显卡的 Intel 轻薄本上可以启动，但推理速度和稳定性需要继续实机评估。
- faster-whisper、Demucs、ACE-Step 模型下载受网络影响，最终应提供可复现的离线资源包或安装器下载流程。
- 当前还没有安装器、图标签名、自动更新、崩溃上报和模型管理器。

## 4. 性能痛点与系统瓶颈

### 启动速度

启动入口为 `ui/main_window.py` 的 `main()`。启动时会创建 `QGuiApplication`、加载 QML、注册 `audioWorkbench` 桥对象。

当前潜在启动瓶颈：

- 初始化 `WorkbenchBridge` 时会创建运行目录。
- 会加载用户配置和最近播放状态。
- 会扫描 `save/` 歌曲库并尝试恢复第一首/最近歌曲。
- 会执行旧工程输出迁移逻辑。

如果用户 `save/` 目录很大，首屏加载可能变慢。后续建议把歌曲库扫描和旧数据迁移改成后台任务，并在 UI 中显示“正在加载曲库”。

### 运行时高负载操作

以下操作是当前主要性能瓶颈：

- 导入歌曲：复制源文件、ffmpeg 标准化、Demucs 分离、歌词生成、写入 manifest。
- 人声分离：Demucs 在 CPU 上通常是分钟级耗时。
- 歌词识别：faster-whisper 首次加载模型慢，CPU 模式下识别较慢。
- 跑调渲染：整段人声音频进行 F0/重采样/DSP 处理，长歌内存峰值较高。
- 改词唱：ACE-Step 本地 HTTP 服务启动慢，CPU 推理慢，且输出质量依赖模型和提示词。
- 混音导出：整首歌加载、效果链、VST/编码会带来 CPU 和内存峰值。

### 并发与异步处理现状

当前已经采用 Qt 推荐的后台任务模式：

- `ImportSongWorker`：导入歌曲。
- `LyricsGenerationWorker`：歌词识别/生成。
- `ToneDeafRenderWorker`：跑调渲染。
- `ExportMixWorker`：混音导出。
- `LyricRewriteWorker`：改词唱任务。

ACE-Step 模型服务使用 `QProcess` 启动，应用侧用 `QTimer` 轮询模型健康状态。Demucs、ffmpeg、rubberband 等外部工具通过子进程执行。

这套策略基本符合“GUI 主线程只负责渲染和事件响应，耗时任务放到后台”的方向。后续仍需重点优化：

- 减少 `ui/main_window.py` 中同步文件扫描。
- 限制长音频整首读入内存的次数。
- 给日志增加轮转，避免长期使用后 `app.log` 过大。
- 对歌曲切换、按钮连点、模型启动/停止增加更明确的状态机和互斥。

## 5. 配置文件与状态管理

### 配置存储

当前已经新增独立运行态目录 `user_data/`：

```text
user_data/
├─ config.json   # 用户偏好和系统配置
├─ recent.json   # 最近歌曲、最近状态
├─ logs/
│  └─ app.log    # 应用状态日志
└─ cache/        # 缓存目录
```

目前持久化内容包括：

- 播放模式。
- 歌曲根目录。
- 人声音量和伴奏音量。
- 跑调程度。
- 歌词对齐偏移。
- 最近歌曲。

### 歌曲工程存储

每首歌导入后会在 `save/` 下生成独立工程目录，目录内包含：

- 原始音频副本。
- 标准化音频。
- stems 分离结果。
- 歌词文件。
- 改词唱生成/替换结果。
- `project.json` manifest。

原则上，每首歌的分离结果、歌词和改词相关文件都应留在对应的 `save/<歌曲名>/` 下，避免散落到项目根目录或其它临时目录。

### 日志系统

当前日志是轻量文本日志：状态变化会追加写入 `user_data/logs/app.log`。这对开发调试够用，但还不是完整生产级日志系统。

后续建议：

- 引入 Python 标准 `logging`。
- 增加日志等级：INFO/WARNING/ERROR。
- 增加按大小或日期轮转。
- 重要异常带堆栈。
- 打包版提供“打开日志文件夹”入口，方便客户反馈问题。

### 后台任务模式

文件：`ui/main_window.py`

```python
class ImportSongWorker(QObject):
    finished = pyqtSignal(object)
    failed = pyqtSignal(str)

    def run(self) -> None:
        try:
            self.finished.emit(import_single_song(self.config))
        except Exception as exc:
            self.failed.emit(str(exc))
```

说明：耗时任务用 `QObject + QThread` 方式放到后台执行，完成后通过信号把结果发回主线程。

## 当前结论与下一步建议

### 当前状态

- 项目已经具备可运行的 PyQt6/QML 桌面应用雏形。
- 歌曲导入、播放、分离、歌词、跑调、配置持久化、便携版打包等核心链路已经打通。
- 跑调功能是当前可交付度最高的音频处理能力，但仍需针对少量歌曲的尾音残留、音色变化、双声感继续优化。
- 改词唱已接入 ACE-Step 方向，但对轻薄本、本地交付体积、推理速度和真实歌声音色保持仍是高风险项。

### 建议优先级

1. 稳定桌面基础体验：歌曲导入、播放切换、删除/清空确认、歌词同步、日志、异常提示。
2. 固化跑调处理：保留当前最优版，继续处理原唱残留、双声、长句音色变化。
3. 打包交付工程化：从便携版升级到安装器，补齐离线资源包、模型目录、日志入口。
4. 拆分 `ui/main_window.py`：把配置、歌曲库、ACE 管理、任务调度拆成独立模块。
5. 改词唱单独立项验证：先确认目标客户机器配置、可接受体积、可接受耗时，再决定 ACE-Step、本地轻量模型或云端服务方案。

### 给项目经理的风险提示

- Python 桌面应用可以高效接入 AI 和音频生态，但商业交付重点不在“能跑”，而在“普通客户电脑上稳定、不卡、无需手动配环境”。
- 真正影响交付的不是主程序体积，而是 Demucs、ACE-Step、torch、模型权重和运行时的组织方式。
- 如果客户电脑普遍没有 NVIDIA GPU，改词唱应谨慎承诺实时性和高质量，建议作为“高级功能/可选模型包/云端服务”规划。
- 当前最适合先做 MVP 交付的是：歌曲导入、分离、歌词、跑调、混音导出和良好的本地工程管理。
